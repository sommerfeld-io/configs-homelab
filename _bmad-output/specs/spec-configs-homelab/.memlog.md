- (decision) Why: combination of a pain to solve (manual setup produces silently-diverging 'snowflake' machines -- NTP-drift and Docker cross-host incidents) and a vision to realize (every machine provably identical, disposable -- cattle not pets). Affects: Sebastian, sole operator and builder of this personal homelab fleet
- (capability) CAP-1 (from PRD FR-1): intent - operator can provision/rebuild any node to its full declared config in one pass via its role's playbook (desktop/server/raspi). success - requires no manual step beyond the accepted bootstrap list; two nodes of the same role converge identically
- (capability) CAP-2 (from PRD FR-2): intent - operator can make one node differ on purpose via a dedicated host group or scoped playbook, without changing the shared role definition. success - the exception node diverges only as declared; the shared role definition is unchanged for other nodes of that role
- (capability) CAP-3 (from PRD FR-3): intent - operator can check any node against its role's declared OS/security baseline on demand. success - running the matching InSpec profile returns pass/fail against the declared baseline
- (capability) CAP-4 (from PRD FR-4): intent - every node continuously reports operational telemetry (incl. clock/time-sync health) to Grafana Cloud without requiring manual per-node checking. success - an alertable condition (e.g. NTP desync) surfaces in Grafana Cloud without the operator manually checking that node
- (capability) CAP-5 (from PRD FR-5): intent - Ansible role changes are exercised by an automated multi-Ubuntu-version test matrix before reaching any real node. success - a role change breaking a supported Ubuntu version fails CI before merge
- (capability) CAP-6 (from PRD FR-6): intent - an in-progress role fix is isolated from nodes already running the last-known-good config until merged and re-applied. success - nodes on last-known-good config show no change until the fix branch merges and re-runs
- (capability) CAP-7 (from PRD FR-7, using the architecture spine's corrected/narrower rule, not the PRD's overclaim): intent - docs stay structurally aligned with ansible/playbooks/ -- one doc per playbook. success - every playbook has exactly one corresponding docs/ansible/playbooks/*.md; renaming/removing a playbook renames/removes its doc in the same change
- (capability) CAP-8 (from PRD FR-8): intent - every currently-manual bootstrap step is documented with an explicit disposition (permanently accepted or tracked to close). success - no manual step in the docs list is left untagged
- (capability) CAP-9 (from PRD FR-9): intent - the sudoers NOPASSWD workaround needed on newer Ubuntu is resolved so it no longer appears in the manual-steps list. success - GitHub issue #160 is closed and the docs manual-steps list no longer includes the sudoers workaround
- (constraint) All node-configuration secrets via Ansible Vault only, referenced directly by variable name, never plaintext (also AD-6 in the architecture spine) -- bends design: no ad hoc per-playbook secret handling is allowed
- (constraint) Success/progress measurement stays qualitative only -- no time-savings instrumentation or dashboard is to be built; rules out any capability work that would add measurement infrastructure for this
- (constraint) Architecture invariants in ARCHITECTURE-SPINE.md (adopted companion, AD-1..AD-9) are binding for all capability work -- state ownership, role placement, per-machine exception mechanisms, dependency pinning, and CI scope are governed there and not restated in this kernel
- (note) Non-goals distilled from PRD Sec5, using the architecture spine's verified correction for the InSpec EOL date (Aug 2027, not the PRD's stated Apr 2026)
- (decision) Non-goal: bare-metal Pi provisioning (SD-card imaging, first-boot setup) -- distinct problem space (cloudmesh-pi-burn/MAAS), governs from first boot onward only
- (decision) Non-goal: expanding InSpec's scope to catch NTP-sync / cross-host Docker-consistency incidents -- compliance stays scoped to the OS/security baseline; observability is the layer for that
- (decision) Non-goal: automating Docker registry login -- credential-storage risk not worth it for a once-per-machine task
- (decision) Non-goal: formal backup/recovery tooling beyond what exists (GitHub repo backup, Ansible SSH-key recreation, password-login fallback) -- vault/sudo passwords remain one accepted, bounded risk
- (decision) Non-goal: seeking outside contributions or adoption of the public repo

- (decision) Non-goal: a dedicated maintenance-burden signal/mechanism -- noticing maintenance burden already happens naturally as part of how the project is run
- (decision) Success signal: a node reinstalled via its role's playbook reaches full baseline compliance with no manual intervention beyond the documented accepted steps, and drift found on one node of a role is corrected fleet-wide via a single Ansible run.
