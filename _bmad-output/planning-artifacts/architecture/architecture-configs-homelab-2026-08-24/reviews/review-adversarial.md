# Adversarial Review — Architecture Spine: Homelab Configs

Reviewer: adversarial gate (BMad-method Reviewer Gate)
Target: `_bmad-output/planning-artifacts/architecture/architecture-configs-homelab-2026-08-24/ARCHITECTURE-SPINE.md`
Method: construct concrete two-unit scenarios (a new playbook, role, InSpec profile, or per-machine exception) where each unit obeys every AD to the letter yet the pair is incompatible, ambiguous, or unenforced. Findings below are grounded against the actual repository state as of 2026-08-24 wherever real evidence exists (marked "existing evidence"); the rest are constructed near-future scenarios that follow directly from the spine's own examples (marked "constructed").

---

1. **AD-5(a) vs AD-5(b) — no rule for a hardware-attachment trigger that co-occurs with a capability trigger** *(existing evidence)*
   - **Scenario:** `ansible/playbooks/raspi.yml` handles pi4-01's and pi4-02's physically-attached USB HDDs via mechanism (a): extra plays appended inside the group playbook, scoped to `pi4-01.fritz.box` / `pi4-02.fritz.box`. `ansible/playbooks/desktop-media.yml` handles caprica's physically-attached USB HDDs (two of them, via `common/mount-disk`) via mechanism (b): a wholly separate playbook, alongside the `media/jellyfin` role.
   - **Why both compliant:** Both are textbook "physical/hardware attachment unique to one machine" per AD-5(a)'s own trigger language. The raspi.yml authors read it as (a) because the group playbook already existed and appending was cheapest. The desktop-media.yml author reads it as (b) because the hardware attachment happens to co-occur with a capability (Jellyfin) that AD-5(b) explicitly targets. Nothing in the Rule says which trigger wins when both apply to the same unit of work.
   - **Incompatibility:** Two structurally identical "unique hardware attached to one host" cases are already implemented with two different mechanisms in the same repo, with no textual tiebreaker. A third contributor adding a new USB-attached-drive case (e.g., a new Pi with a drive plus no accompanying service) has two valid precedents to copy and no rule saying which is authoritative going forward.

2. **AD-5(b) — "targeting the host(s) directly by name" is already violated by an existing (b)-mechanism playbook** *(existing evidence)*
   - **Scenario:** AD-5(b)'s Rule text specifies the mechanism as "a separate playbook targeting the host(s) directly by name." `desktop-media.yml` does this correctly (`hosts: caprica.fritz.box`). But `desktop-steam.yml` — also a "specific service/capability not every node of a role needs" case (Steam isn't installed via `desktop.yml`) — targets `hosts: ubuntu_desktop`, the entire group, not a named host.
   - **Why both compliant:** Both are legitimately "a specific capability" playbooks per the trigger. `desktop-media.yml` follows the letter of "by name." `desktop-steam.yml` follows the spirit ("not every node of a role needs it" doesn't literally require single-host targeting if the intended audience genuinely is "every desktop, but not the servers/pis") while diverging from the literal mechanism description.
   - **Incompatibility:** A future contributor building a similar "some nodes of a role, not others" capability can point to either precedent — by-name targeting (per the Rule's literal text) or by-group targeting (per existing practice) — producing inconsistent host-targeting conventions across (b)-style playbooks with no lint catching the divergence.

3. **AD-5(c) — the prescribed mechanism ("dedicated capability group") is already bypassed by inline group-unions doing the same job** *(existing evidence)*
   - **Scenario:** `grafana-agents.yml` (Grafana Cloud monitoring) is a capability that cuts across all three node-role groups — the exact trigger AD-5(c) names, whose canonical example is the dedicated `ollama` capability group in `hosts.yml`. Yet `grafana-agents.yml` targets `hosts: ubuntu_desktop:ubuntu_server:raspi` inline, with no corresponding capability group in the inventory. `repositories.yml` does the same for its cross-cutting "clone repos on every node" logic.
   - **Why both compliant:** The `ollama` group satisfies AD-5(c) exactly as written. `grafana-agents.yml`/`repositories.yml` satisfy the same underlying need (a cross-cutting capability) without inventing "a fourth ad hoc mechanism" (the thing AD-5 explicitly prevents) — an inline group-union isn't a new mechanism, arguably just Ansible's native group-set syntax, so it's arguably not even "using" mechanism (c) at all, just avoiding the need for it.
   - **Incompatibility:** The Rule prescribes what (c) looks like when invoked but never says inline group-unions are disallowed as an alternative for the identical trigger. A next contributor adding a new cross-node-role capability (e.g., a shared backup agent) has two live, equally-compliant precedents — build a real capability group, or just union group names in the playbook's `hosts:` line — with opposite maintainability properties (host-vars support vs. none) and no rule forcing a choice.

4. **AD-4 — a role that is already generic-by-construction is placed locally, contradicting the Rule's own placement test** *(existing evidence)*
   - **Scenario:** `ansible/roles/common/mount-disk` takes only `mount_disk_uuid`, `mount_disk_path`, and `default_user` as inputs and mounts any UUID at any path via `ansible.posix.mount` — zero homelab-specific assumptions are baked into the role itself (the homelab-specific values live in the *playbooks* that call it: `raspi.yml`, `desktop-media.yml`). By AD-4's own test — "generic, reusable, OS-level capability with no homelab-specific assumptions" → submodule — this role reads as submodule material, yet it lives in local `ansible/roles/common/`.
   - **Why both compliant:** The role's *author* can defend the local placement: "it deploys a homelab-specific concrete instance" is true at the call-site (specific UUIDs, specific paths for specific Pis). A hypothetical *reviewer* extracting the same logic into the submodule can equally defend that placement by reading the role body in isolation, which contains no homelab-specific content whatsoever.
   - **Incompatibility:** No lint enforces role placement (`.ls-lint.yml` explicitly `ignore`s `ansible/roles` wholesale; `.folderslintrc` only enforces structural subfolder shape, not genericity). A next contributor adding a similarly parameterized utility role (e.g., "mount any network share," "create any systemd timer") can place it in either location under a fully defensible reading of AD-4, and nothing forces consistency with the `mount-disk` precedent either way.

5. **AD-4 — a composite role split differently by two contributors** *(constructed)*
   - **Scenario:** Contributor A adds Grafana Alloy support entirely as the existing monolithic local role `ansible/roles/grafana-cloud/alloy` (install + homelab-specific scrape/relabel config together), defensible as "deploys a homelab-specific concrete instance." Contributor B, working from the same AD-4 text, decides the *installation* half ("install the Alloy binary, register the systemd unit") is "generic, reusable, OS-level capability with no homelab-specific assumptions" and factors it into `ansible-roles-collection/alloy`, leaving only the scrape config as `common/grafana-cloud/alloy-config`.
   - **Why both compliant:** Each half of AD-4's Rule text applies to a different slice of the same capability; AD-4 gives no guidance on where to draw the line inside a role that has both a generic mechanism and a homelab-specific configuration payload (`mount-disk` sidesteps this by keeping the generic part 100% parameter-driven and never touching config content — Alloy's scrape config doesn't factor as cleanly).
   - **Incompatibility:** If both contributions land (e.g., across two PRs reviewed independently), the repo ends up with duplicate/overlapping Alloy-installation logic — one path via the pre-existing monolithic local role, one via the newly split submodule role — each individually AD-4-compliant, jointly redundant and confusing about which "owns" installation.

6. **AD-2/AD-1 — no CI mechanism actually blocks "just one more imperative script"** *(existing evidence)*
   - **Scenario:** `.ansible-lint.yml` puts `command-instead-of-module` and `no-changed-when` in `warn_list` (non-blocking) rather than `enable_list`. Six of the twelve provisioning playbooks (`all.yml`, `desktop.yml`, `grafana-agents.yml`, `ollama.yml`, `raspi.yml`, `server.yml`) are fully excluded from `ansible-lint` via `exclude_paths` (tracked as pre-existing tech debt, GitHub issue #172, already noted as Deferred in the spine). `repositories.yml` (not excluded) already contains `ansible.builtin.shell: gh repo edit ...` run in a loop over every tracked repo on every provisioning run against `hosts: localhost` — a repeatable, multi-target imperative action, exactly the shape AD-2 says "must be an idempotent Ansible task," implemented as a raw shell command instead.
   - **Why both compliant:** It's technically inside an Ansible playbook (satisfies "must be an [...] Ansible task" at the file level), and `no-changed-when`/`command-instead-of-module` only warn — CI is green either way.
   - **Incompatibility:** AD-2's Rule text draws a bright line ("must be an idempotent Ansible task" vs. "genuinely one-time, single-node bootstrap"), but no lint, CI gate, or naming convention actually enforces which side of that line a new task falls on — especially inside the six playbooks with no ansible-lint coverage at all. Two future contributors adding "just one more" repeatable action can both point to `repositories.yml`'s shell-loop as precedent that this is fine, while a third who writes a proper idempotent module-based task gets no CI credit for the extra rigor. The Rule is enforced by discipline only.

7. **AD-6 "Binds: all" creates a false, unsatisfiable obligation over CI secrets** *(existing evidence)*
   - **Scenario:** AD-6's Binds is `all`. Read literally, this requires every secret in the system to live in an Ansible-Vault-encrypted file under `ansible/vars/`. But `.github/workflows/pipeline.yml` consumes `secrets.DOCKERHUB_USER`, `secrets.DOCKERHUB_TOKEN`, and `secrets.GITHUB_TOKEN` — GitHub Actions' own encrypted-secrets store, which CI runners need at build/lint time with no Ansible Vault password available or appropriate to distribute there.
   - **Why both compliant:** A contributor adding a new CI credential (e.g., a new registry login for a future workflow) can honestly say "AD-6 binds all, so per the Rule this must go in the vault" and be textually correct, while another contributor treats GitHub Actions secrets as self-evidently out of scope — also textually defensible, since AD-6's Rule text only actually describes node-configuration secrets (`vault.yml`, `grafana-vault.yml` referenced by tasks), not CI/build-time secrets.
   - **Incompatibility:** The spine gives no explicit carve-out for CI-pipeline secrets vs. node-configuration secrets, so "Binds: all" is either unsatisfiable (as already proven by the existing, unavoidable use of GitHub Actions secrets) or silently non-binding for an entire class of real secrets in the system — and nothing marks which reading is correct.

8. **AD-9 — the Rule only constrains one direction, leaving stale/orphaned docs unaddressed** *(constructed, mechanism gap is existing evidence)*
   - **Scenario:** Contributor A renames `desktop-media.yml` → `desktop-jellyfin.yml` for clarity, adds `docs/ansible/playbooks/desktop-jellyfin.md`, and deletes the now-orphaned `desktop-media.md` (reasoning: "AD-9 says exactly one doc per playbook, so a doc for a playbook that no longer exists violates that"). Contributor B deletes an obsolete playbook (e.g., `scan.yml`, if superseded) but leaves `docs/ansible/playbooks/scan.md` in place (reasoning: "AD-9's Rule only says every *playbook* needs a doc; it says nothing about deleting a doc when its playbook goes away, so I haven't violated anything by leaving it").
   - **Why both compliant:** AD-9's Rule text is genuinely one-directional ("every playbook... has exactly one corresponding doc") and silent on the reverse mapping or on deletion/rename events.
   - **Incompatibility:** No mechanism would catch either choice — `lychee` only validates that links resolve, not doc/playbook coverage; `.folderslintrc` only validates folder-structure shape (`docs/ansible/**`), not per-file correspondence; `docs:generate` only copies a few hardcoded files (README, LICENSE, one role README) and doesn't scaffold or prune per-playbook docs. The repo ends up with an inconsistent stale-doc policy purely by contributor preference, and reviewers have no spine text to cite either way.

9. **AD-9 is already contradicted by the repo's own doc-generation tooling** *(existing evidence — strongest finding)*
   - **Scenario:** AD-9's Rule states plainly: "`ansible/roles/`... carr[ies] no docs-mirroring requirement." Yet `taskfile.yml`'s `docs:generate` task already does exactly that for one role: it copies `ansible/roles/grafana-cloud/alloy/README.md` into `docs/ansible/roles/grafana-cloud/alloy.md` — a role-level docs mirror, generated by the project's own build tooling, that AD-9 explicitly disclaims.
   - **Why both compliant:** A contributor citing the Rule text ("roles carry no docs-mirroring requirement") can reject a PR that adds a doc mirror for another role (e.g., `common/mount-disk/README.md` → `docs/ansible/roles/common/mount-disk.md`). A contributor citing established, currently-shipping precedent (the Alloy role is already mirrored, and the generation task exists specifically to do this) can defend adding the same for any other role.
   - **Incompatibility:** This isn't a hypothetical clash — it's a live contradiction between the ratified AD-9 text and the actual `taskfile.yml`. The spine, as written, is already false about the system it claims to describe, meaning "docs mirror playbooks only" cannot be treated as a hard invariant without either amending the Rule or removing the existing role-doc generation step.

10. **AD-7 — "may float" gives no criterion for which owned dependencies pin vs. float, and two owned dependencies already diverge** *(existing evidence)*
    - **Scenario:** AD-7's Rule says an operator-owned dependency "*may* intentionally float on a branch... when the intent is to always track latest" — permissive, not prescriptive. In the Stack table, `sommerfeld-io/inspec-profiles` (operator-owned) floats on `main`, while `ansible-roles-collection` (also operator-owned, also referenced in AD-7's own Binds) is pinned to tag `v0.15.0`.
    - **Why both compliant:** "May float" doesn't mean "must float" — pinning your own repo is never forbidden by the Rule, so both the floating InSpec-profile dependency and the pinned submodule are simultaneously valid under the same sentence.
    - **Incompatibility:** A future contributor adding a new operator-owned dependency (a second submodule, a new shared InSpec profile) has zero criterion in the spine for choosing pin-vs-float, and no CI checks for internal consistency between owned-dependency pinning strategies — the two existing owned dependencies already model both choices side by side with no stated rationale distinguishing them.

11. **AD-7's Binds are scoped too narrowly, hiding an existing pin-vs-float inconsistency in the exact failure mode AD-7 exists to prevent** *(existing evidence)*
    - **Scenario:** AD-7 Binds only `tests/inspec/*` and "the ansible-roles-collection submodule reference." But `docker-compose.yml` — used by CI lint jobs — already pins third-party tool images inconsistently: `cytopia/yamllint:latest` and `lycheeverse/lychee:latest` float on `latest` (unpinned), while `pipelinecomponents/ansible-lint:0.79.33`, `lslintorg/ls-lint:1.11.2`, `sommerfeldio/folderslint:0.26.1`, and `chef/inspec:5.22.76` are pinned to exact versions.
    - **Why both compliant:** Neither the floating nor the pinned image tags are bound by AD-7 at all — the Binds list simply doesn't reach `docker-compose.yml`. Every image tag in that file is, per the letter of the spine, ungoverned.
    - **Incompatibility:** This is exactly the risk AD-7 exists to "prevent: an upstream third party silently changing what 'passing' means" — yet it's already happening, invisibly to the spine, for two of ten CI tool images. A next contributor adding a new lint container is free to pin or float with no guidance, and the spine cannot even be cited to fix the existing `:latest` pins because they fall outside its stated Binds.

12. **AD-1/AD-2/AD-3 "Binds: all" vs. VMs named in scope but absent from the Structural Seed** *(existing evidence of the gap, constructed scenario)*
    - **Scenario:** The spine's own scope and "Deployment & environment" section name "VMs" as part of the live fleet. AD-1, AD-2, and AD-3 all state `Binds: all`. Yet `ansible/hosts.yml` (the Structural Seed's actual inventory) has no VM group or host at all, and the only VM-related role in play (`ansible-roles-collection/virtualization`, included from `server.yml`) sets up the *hypervisor* on caprica — it does not declare or converge any VM guest's configuration.
    - **Why both compliant:** Contributor A provisions a new VM guest entirely by hand, reasoning "there's no inventory pattern for VMs yet, so AD-1's 'the declaration is the only source of truth' has nothing to attach to until one is invented — I'm not maintaining a 'separate state store,' I'm just not in the declared system yet." Contributor B insists a new VM guest must be inventoried and Ansible-managed from day one because "Binds: all" is unambiguous and VMs are explicitly in scope.
    - **Incompatibility:** The spine simultaneously claims universal binding ("all") and includes a class of fleet member (VMs) for which the Structural Seed provides no onboarding pattern, group, or playbook convention. Two contributors can make opposite, individually defensible choices about whether a given VM is "in" the declared system at all, with no inventory convention, lint, or Rule text to arbitrate.

13. **AD-8 — "never executes a playbook against... a containerized target" doesn't obviously distinguish smoke-testing from the redundant role-testing matrix it's meant to prevent** *(constructed)*
    - **Scenario:** Contributor A adds a CI job that spins up a throwaway Docker container solely to run `ansible-playbook --syntax-check` / `--check` against `desktop.yml` as a fast smoke test for playbook-level regressions (not role behavior) — arguing this serves AD-8's stated concern ("prevent... assuming the submodule's CI validates this repo's own playbooks") without being "a redundant second role-testing matrix" (the thing AD-8 actually prohibits). Contributor B rejects the same PR citing the Rule's literal text: "this repo's own CI... never executes a playbook against a live or containerized target," full stop, no exception for syntax-only or dry-run smoke tests.
    - **Why both compliant:** AD-8's stated *Prevents* clause and its literal *Rule* clause don't fully coincide — the Prevents clause is about redundant role-testing and about wrongly assuming submodule CI covers this repo's playbooks (which a containerized syntax check would actually help with), while the Rule's literal text is an unconditional ban on playbook execution against any containerized target, regardless of purpose.
    - **Incompatibility:** A narrowly-scoped playbook smoke test can be simultaneously "clearly serves AD-8's purpose" and "clearly violates AD-8's literal text," and the spine gives no way to resolve which controls — leaving this exact category of contribution (playbook-level CI smoke testing, distinct from role testing) undecidable without an amendment.

14. **AD-4's same-named-layering order convention ("submodule role always included first, local role second") has no enforcement mechanism** *(existing evidence for the gap; current code happens to comply)*
    - **Scenario:** `raspi.yml` and `server.yml` both currently include `ansible-roles-collection/taskfile-dev` before `common/taskfile-dev`, matching AD-4's stated ordering. But nothing checks this — `ansible-lint`'s enabled rules don't inspect semantic ordering of `include_role` calls, and there's no custom lint for it. A future contributor adding a new same-named pair (e.g., a `common/hardening` layering on `ansible-roles-collection/hardening`) could reverse the order — deliberately (reasoning "the local override should establish a baseline that the generic role then refines," a legitimate operational pattern in other Ansible codebases) or accidentally — and nothing in CI would flag it.
    - **Why both compliant:** Both orderings "include the submodule role" and "include the local role" somewhere in the playbook; AD-4's Rule text asserts a specific order but provides no verification, so a reversed-order playbook would pass every existing lint/CI gate while silently violating the stated convention.
    - **Incompatibility:** This is a Rule that is fully specified but entirely unenforced — same category as AD-2's imperative-script boundary (#6 above) but specific to role-inclusion order, meaning layering behavior can silently diverge between contributions with no mechanism to catch it, only code review discipline.

## Summary

14 concrete findings identified (minimum standard was 10). Of these, findings #1, #2, #3, #4, #6, #7, #9, #10, #11, #12 are grounded in evidence already present in the repository today — meaning several of the "two incompatible units" this review was asked to construct hypothetically already exist side by side in the current codebase, ratified or not. Findings #5, #8, #13, #14 are constructed near-future scenarios that follow directly from gaps already visible in the spine's text and the repo's existing lint/CI configuration.

Highest-severity: #9 (AD-9 directly contradicted by shipping tooling) and #1/#3 (AD-5's three mechanisms already applied inconsistently to structurally identical triggers) — these represent the spine ratifying a rule that current practice already violates, not just a risk of future divergence.
