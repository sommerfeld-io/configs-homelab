# Architecture Spine Review — Rubric

## Overall verdict

The spine is well-grounded: every AD I spot-checked against the live repo (task naming, role-layering order, the three per-machine-exception mechanisms, the vault edit path, the InSpec profile-version lockstep, CI's lint-only scope) matched the actual code exactly, and the Capability → Architecture Map covers FR-1 through FR-9 with no gaps. It fixes the real divergence points a downstream story-writer would hit. The two structural problems worth blocking on: the Chef/InSpec EOL item in Deferred is stated as a future risk but, per the stated current date, has already passed, so it is not safe to leave open as written; and the deployment diagram's GitHub→node edges directly contradict AD-8's own claim that this repo's CI never touches a live node. A handful of lower-severity accuracy gaps (submodule pin-vs-float ambiguity, an unacknowledged existing docs/roles exception, a cosmetic Pi-numbering error, an unverifiable issue reference) round out the findings.

## Findings

- **high** Deferred Chef/InSpec EOL item is already past its trigger date, not a future risk (Deferred section, "Chef/InSpec ecosystem EOL risk") — the bullet says "InSpec 5.x Apr 2026" EOL is a risk to "revisit if/when it becomes a practical problem," but the spine's own `created`/`updated` date is 2026-08-24 — four months after that EOL date. The Stack table still pins the CI runner to `chef/inspec 5.22.76` with no successor named and no version-check step in CI. This deferred item is a live risk today, not something safe to leave open — it fails the checklist's own bar ("a Deferred item should be safe to leave open, not a live risk"). Fix: convert to an Open Question or a near-term backlog item; at minimum, add an explicit trigger check (e.g., confirm whether the `chef/inspec` image is still receiving updates) rather than an open-ended "if/when."

- **high** Deployment diagram's edges contradict AD-8 (ARCHITECTURE-SPINE.md, second mermaid block under "Deployment & environment," lines ~141–158) — `GH -. "provisions from" .-> UD/US/RP` draws GitHub as the thing that provisions the fleet groups. AD-8 states plainly that "this repo's own CI ... never executes a playbook against a live or containerized target," and the actual mechanism (`ansible/taskfile.yml`'s shared `&ansible-cmd` anchor) is a human running `ansible-playbook ... --ask-become-pass --ask-vault-pass` locally — not anything GitHub does. As drawn, a downstream reader would reasonably conclude CI drives provisioning, which is the opposite of AD-8's rule. Fix: relabel/redirect the edge to show the operator as the actor (e.g. "operator runs, using code hosted at" GH→operator→fleet, or simply drop the misleading "provisions from" verb since GitHub only hosts the code and CI).

- **medium** AD-7's "pin third-party, float own" rule doesn't resolve what it should mean for the `ansible-roles-collection` submodule, even though the submodule reference is explicitly named in AD-7's own **Binds** line — Every `ansible/taskfile.yml` task shares `git submodule update --remote` in its `&ansible-cmd` anchor, which always fast-forwards the submodule to the latest commit on its tracked branch before running a playbook — i.e., it behaves as a floating dependency in practice, the same category as `sommerfeld-io/inspec-profiles`. But the Stack table lists it as a fixed version, `v0.15.0`, implying a pin. Checked against the actual repo state, the committed submodule SHA is already `v0.15.0-5-gea3ab01` (5 commits past that tag), confirming it drifts past the table's stated version in normal operation. Fix: state explicitly whether `ansible-roles-collection` is intentionally floating (like `inspec-profiles`) or should be pinned by tag/SHA (in which case `git submodule update --remote` is the wrong mechanism and should be replaced), and correct the Stack table to reflect that decision rather than a point-in-time version.

- **low** AD-9 ("Docs mirror playbooks only") doesn't acknowledge an existing, deliberate exception already live in the repo — `docs/ansible/roles/grafana-cloud/alloy.md` exists, is registered in `mkdocs.yml`'s nav, and has its own multi-commit history of intentional edits (documenting required vars and a sudoers caveat). AD-9's Rule ("`ansible/roles/`... carry no docs-mirroring requirement") is technically not violated by this (no *requirement* ≠ *prohibited*), but the section title and framing read as "playbooks are the only thing docs mirror," which doesn't match observed reality and leaves it unclear to a story-writer whether this file is legacy debt to remove or a pattern that may recur for other roles. Fix: add one line to AD-9 either ratifying this as a narrow, permitted exception (and stating when a role doc is warranted) or flagging it explicitly for cleanup.

- **low** Deployment diagram's Pi-node label is inaccurate (ARCHITECTURE-SPINE.md, second mermaid block, `RP["raspi<br/>pi4-01..05, pi5-01"]`) — the `..` range shorthand implies `pi4-01` through `pi4-05` inclusive, i.e. 5 machines. Actual inventory (`ansible/hosts.yml`) has only `pi4-01, pi4-02, pi4-03, pi4-05` (no `pi4-04`) plus `pi5-01` — exactly as the driving PRD's own glossary spells out ("pi4-01/02/03/05 and pi5-01") precisely to avoid this ambiguity. Fix: spell out the four numbers instead of using a range, matching the PRD's own phrasing.

- **low** Deferred item's GitHub issue reference could not be verified (Deferred section, "GitHub issue #172") — `gh issue view 172` against `sommerfeld-io/configs-homelab` returns "could not resolve to an issue," while the neighboring issues cited elsewhere in the spine/repo (#160, and #174 found nearby) resolve fine. This traces back to a pre-existing TODO comment in `.ansible-lint.yml` (not invented by the spine), so it's not a spine-authoring defect, but the spine repeats the reference as "pre-existing tracked tech debt" without it being independently verifiable as tracked anywhere. Fix: confirm issue #172 still exists (may have been deleted/renumbered/transferred) before relying on it as the record of this tech debt; if it's gone, open a replacement issue or fold the note directly into the spine/Deferred text.

- **info** Everything else spot-checked matched the live repo exactly: task-naming convention (`Category  ----  Subcategory  ----  Action`, verified in `ansible-roles-collection/{bash,docker}/tasks/main.yml`), AD-4's submodule-then-local role layering (`../roles/ansible-roles-collection/taskfile-dev` before `../roles/common/taskfile-dev` in `desktop.yml`/`server.yml`/`raspi.yml`), all three AD-5 exception mechanisms (`raspi.yml`'s per-host disk-mount plays, `desktop-media.yml` targeting `caprica.fritz.box` directly despite its `ubuntu_server` group membership, the `ollama` cross-cutting inventory group), AD-6's sanctioned vault-edit path (`ansible:vault` / `ansible:vault:grafana` tasks calling `ansible-vault edit`), AD-7's InSpec dependency pinning (`dev-sec/linux-baseline` tag `2.9.0`, `sommerfeld-io/inspec-profiles` on branch `main`, all four profiles at version `0.92.1`), AD-8's CI scope (`pipeline.yml` runs lint/InSpec-check/docs/release only, no playbook execution), and the Stack table's `chef/inspec 5.22.76`, `ansible-lint 0.79.33`, and go-task `3.42.1` versions (all found pinned identically in `docker-compose.yml`/`pipeline.yml`/`taskfile.yml`). Both mermaid diagrams are syntactically valid and substantive (not decorative) — the first accurately conveys the dual-verification design paradigm; the second's structure is sound aside from the AD-8 contradiction noted above. Capability → Architecture Map covers FR-1 through FR-9 with no missing rows.
