From a flaky door
to a small, steady droplet

A hobby fantasy-hockey app for three people, a Raspberry Pi behind a Fritzbox that never quite let the internet in, and a decision to stop opening doors into the home network. One DigitalOcean droplet, built by OpenTofu, dressed by Ansible, watched by Grafana, and meant to run unattended for years.

Technique 1

Constraint Mapping

Before choosing anything, we mapped what must stay true. The map grew from the inside out: why we leave, which secrets must travel, what state lives where.

Why we are moving

The Fritzbox port exposure on the Raspi was unstable, and the user does not want a door into the home network. A small DO droplet answers both. user

Goal: stable gitops-style cloud deployment, extensible to more apps or microVMs, identical locally (task) and in CI.

Technique 3

Failure Analysis

Two failures from the Fritzbox years, three the new setup could invent. Each one leaves a lesson behind.

PAST FAILURE 1

The port that worked only from outside

The port 80 forward worked from the internet, but from LAN or WiFi the router's management UI took priority. It could never be tested locally. user

The new URL is reachable from anywhere, home network included, so this failure disappears. A post-deploy smoke test is a good idea, but in a later epic. coach user
PAST FAILURE 2

Timeouts that monitoring never saw

Random request timeouts from outside while Pi and container monitoring showed no downtime, and the app answered on pi4-0002.fritz.box. Internal monitoring was blind to the external path. user

Monitor from outside too. Use the Grafana Cloud synthetic monitoring already watching other URLs from Frankfurt and Paris. coach user

Foreseeable failures user

Decision: observe first, maybe alert later.

LIKELY

Full disk

Later epic or story: Ansible logrotate and cleanup (lands in E7).

SCARIEST

Too little RAM

OOM kills services, may even restart the droplet.

coach swap file, docker mem_limit and restart: unless-stopped, Alloy MemoryMax in systemd, alert on available memory and OOM kill count. Resize is a one-line OpenTofu change, CPU/RAM only, never disk, to stay reversible.

OBVIOUS

Unreachable from the internet

Covered by the outside probe, and later by the smoke test.

Technique 4

Time Horizon Ladder

Climb the rungs and ask what still holds. The surprise at the top: scale is not the threat, neglect is.

Now
  • Order of work: OpenTofu creates the droplet, Ansible provisions, Ansible deploys the app. user
  • Epic 1 runs fully local through the taskfile; Actions comes later.
  • Docs under docs/cloud/digital-ocean are part of every epic, with kroki.io diagrams and nav item 'Cloud - Digital Ocean'; all GitHub secrets at org level. user
  • A comprehensive Grafana dashboard (CPU, memory, app, containers, all container logs) in grafana-cloud/manifests/git-sync/apps. No alerts yet. user
One year
  • Prefer adding a second droplet over enlarging the first; it may be disposed when no longer needed. Candidates: a test stage (stage=test) or an unrelated app, never a bigger prod. user
  • Droplet as a reusable module or for_each keyed by name and stage, inventory groups per purpose, quantity stays 1. coach
Ten years and beyond
  • The app is a hobby for three people and will stay so: scaling prod is not a driver. user
  • Must run unattended long-term. user
  • Real risks: unattended-upgrades, Dependabot for images, Ubuntu 26.04 LTS end of life, pinned OpenTofu and provider versions. coach
  • OS upgrade path (e.g. 28.04 LTS): no in-place dist-upgrade. Change the image slug, the droplet is replaced, volume and reserved IP re-attach, rerun provision and deploy. A short outage is fine; easiest way wins. coach user

Synthesis

Six connections

Hover a connection to light up the epics it touches. coach

The disposable droplet

Identity (reserved IP), state (volume) and discovery (tag-based dynamic inventory) are independent of the droplet. OS migration means replacing it with no extra tooling, and backup can wait.

E1 / E2 / E8

Inventory frees Ansible from state

Dynamic inventory removed Ansible's need for OpenTofu state, so the shared state question in E5 concerns OpenTofu only.

E2 / E5

Stage, defined once

'stage' appears in the tag, droplet name, inventory group and Alloy label. Define it once and let it flow.

E1 / E2 / E4

Two views, two failure modes

Alloy gives the inside view, synthetic monitoring the outside view. Together they cover both Fritzbox failure modes.

E2 / E4

Neglect is the real risk

Unattended-upgrades, expiring tokens, Ubuntu EOL. At the ten-year rung, the docs are the only memory.
