# Tasks and Linters

The DigitalOcean deployment lives in its own folder, separate from the homelab nodes:

```text
configs-cloud/
  taskfile.yml       # included in the root taskfile with prefix `cloud`
  digital-ocean/
    opentofu/        # droplet, reserved IP, volume and DNS zone
      taskfile.yml   # included with prefix `digital-ocean:opentofu`
    ansible/         # dynamic inventory, playbooks, cloud roles and vars for the droplet
      taskfile.yml   # included with prefix `digital-ocean:ansible`
    tests/molecule/  # one Molecule scenario per role the droplet runs, see Tests
```

## Tasks

All steps run through go-task from the repository root. The tasks wrap `tofu` and `doctl` from the devcontainer; the OpenTofu tasks are defined in and run from `configs-cloud/digital-ocean/opentofu/taskfile.yml`, the Ansible tasks from `configs-cloud/digital-ocean/ansible/taskfile.yml`.

| Task                                                     | What it does                                                                                                                                                                                                                  |
|----------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `task cloud:digital-ocean:opentofu:init`                 | Initialize the OpenTofu working directory (providers, modules)                                                                                                                                                                |
| `task cloud:digital-ocean:opentofu:fmt`                  | Format the OpenTofu files                                                                                                                                                                                                     |
| `task opentofu:validate`                                 | Validate every OpenTofu root (folder with a tracked `versions.tf`, as the CI job `validate-opentofu`; no token or state); initializes without a backend when a first validate fails (needs the network); part of `task lint`  |
| `task cloud:digital-ocean:opentofu:plan`                 | Show the changes OpenTofu would make                                                                                                                                                                                          |
| `task cloud:digital-ocean:opentofu:apply`                | Apply the OpenTofu configuration                                                                                                                                                                                              |
| `task cloud:digital-ocean:opentofu:apply:yes`            | Apply without the confirmation prompt (`-auto-approve`); read `opentofu:plan` first. `prevent_destroy` still protects the volume, the reserved IP and the DNS zone                                                            |
| `task cloud:digital-ocean:ansible:inventory`             | List the droplets found by the dynamic inventory with their groups                                                                                                                                                            |
| `task cloud:digital-ocean:ansible:provision`             | Provision all Ubuntu droplets (time zone, prompt, tools, Docker, swap, cAdvisor, Alloy, MOTD) after waiting for SSH and cloud-init                                                                                            |
| `task cloud:digital-ocean:ansible:deploy-fantasy-hockey` | Deploy the fantasy hockey app to the droplets with the tag `fantasy-hockey` ([Deployment](deployment.md))                                                                                                                     |
| `task cloud:digital-ocean:ansible:all`                   | Run `playbooks/all.yml`: `provision.yml`, then `deploy-fantasy-hockey.yml`, in one Ansible run with one vault password prompt                                                                                                 |
| `task cloud:digital-ocean:ansible:vault:fantasy-hockey`  | Edit the fantasy hockey secrets in `ansible/vars/fantasy-hockey-vault.yml`                                                                                                                                                    |
| `task cloud:deploy:all`                                  | Full pipeline: `opentofu:apply`, then `ansible:all`, with one vault password prompt                                                                                                                                           |
| `task cloud:dns:check -- <dig arguments>`                | Run `dig` in a pinned container (service `dns-check`), e.g. `task cloud:dns:check -- +norec @ns1.digitalocean.com fantasy-hockey.prod.do.sommerfeld.app A`. The devcontainer has no `dig`. See [DNS Zone](dns-zone.md#checks) |
| `task cloud:info`                                        | Print the account, all droplets, reserved IPs and volumes with `doctl`                                                                                                                                                        |
| `task cloud:molecule:test`                               | Run every Molecule scenario for the roles the droplet runs ([Tests](tests.md))                                                                                                                                                |
| `task cloud:molecule:test:<role>`                        | Run one Molecule scenario, e.g. `motd`                                                                                                                                                                                        |

Run `init` once before `plan` and `apply`, and again after provider changes. The OpenTofu and Ansible tasks that need the token and `info` stop early when `DIGITALOCEAN_ACCESS_TOKEN` is not set. See [API Token](api-token.md).

There is no destroy task on purpose. The volume and reserved IP must survive droplet rebuilds, so both have `lifecycle { prevent_destroy = true }` and OpenTofu refuses any plan that would destroy them, including `tofu plan -destroy`, with `Resource instance cannot be destroyed`. The droplet itself stays replaceable.

OpenTofu state stays local in `configs-cloud/digital-ocean/opentofu/terraform.tfstate` for now and is not committed: `.terraform/`, `*.tfstate*` and `*.tfvars` are in `.gitignore`. The single local copy is an accepted risk until state moves to a remote backend in a later epic, so do not delete the working copy while resources exist. The OpenTofu version (`required_version`) and the `digitalocean/digitalocean` provider are pinned exactly in `versions.tf`. The provider lock file `.terraform.lock.hcl` is committed with hashes for every platform the provider is released for, as published by the OpenTofu registry. Dependabot (`opentofu` ecosystem) opens weekly pull requests that bump the provider pin and the lock file together.

## Linters

`task lint` and the `lint` job in the CI pipeline cover `configs-cloud` like the rest of the repository:

| Linter       | Coverage                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| folderslint  | `configs-cloud/*/opentofu`, `configs-cloud/*/ansible` and its `inventory`, `playbooks`, `vars`, `templates/*` and `roles` folders, `defaults`, `files` (with sub-folders, none in use today), `handlers`, `tasks` and `templates` inside each role, and everything under `configs-cloud/*/tests/molecule`, are allowed in `.folderslintrc`                                                                                                                                                   |
| ls-lint      | kebab-case filenames, including `.tf` files                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| yamllint     | all YAML files, including `configs-cloud/taskfile.yml`                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ansible-lint | `configs-cloud` is linted together with `configs-homelab/ansible`, except `playbooks/provision.yml`: it loads the vaulted `grafana-vault.yml` through `vars_files`, which the syntax check cannot decrypt, so it is in `exclude_paths` of `.ansible-lint.yml` like the fleet playbooks. The roles it runs are still linted. `playbooks/deploy-fantasy-hockey.yml` loads its vault with an `include_vars` task, so it is linted. The Molecule playbooks under `tests/molecule` are linted too |
| OpenTofu     | `tofu fmt -check -diff -recursive configs-cloud` (service `lint-opentofu`, keep the image version in sync with the devcontainer's OpenTofu)                                                                                                                                                                                                                                                                                                                                                  |

Before the linters run, `task lint` formats the OpenTofu code with `task cloud:digital-ocean:opentofu:fmt`. The `lint-repo` pre-commit hook runs `task lint`, so OpenTofu files are formatted on every commit and only formatted code reaches the remote repository, which avoids conflicting whitespace changes. Only the OpenTofu code is formatted; all other files are only linted. Locally, the OpenTofu linter therefore checks freshly formatted files; stage the files the hook reformatted and commit again.

Run a single linter with `docker compose up lint-opentofu --exit-code-from lint-opentofu`. CI runs the linters without formatting first, so if the OpenTofu linter fails there, run `task cloud:digital-ocean:opentofu:fmt` and commit the result.

`task lint` also runs `tofu validate` for every OpenTofu root (`task opentofu:validate`). A root is any folder with a tracked `versions.tf`; `.github/workflows/assets/find-opentofu-roots.sh` lists them, so a new root needs no list to be edited. No manual `init` is needed: when a first validate fails, for example because the provider cache in `.terraform/` is missing or does not match the lock file, the task runs `tofu init -backend=false -input=false -lockfile=readonly`, which installs the locked providers without touching the backend, the state or `.terraform.lock.hcl`. Only this first init needs network access; an initialized root validates offline. In CI, the `validate-opentofu` job in `.github/workflows/pipeline.yml` validates the same roots, one matrix entry per root built by the `find-opentofu-roots` job from the same script, but it always runs `tofu init -backend=false -input=false -lockfile=readonly`, then `tofu validate`, in the `ghcr.io/opentofu/opentofu` image of the version the root pins in `required_version`, without a token or state. The job fails unless `required_version` is an exact `x.y.z` version, because the version is the image tag. It needs no Docker Hub login and no submodules. `generate-docs` waits for it.
